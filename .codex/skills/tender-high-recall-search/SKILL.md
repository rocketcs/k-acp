# 商业标书高召回检索

本技能只负责生成和约束检索计划。接口地址、认证、字段和工具调用方法继续以 `tender-search` 为准；不得在本技能中猜测或复制凭据。

## 何时使用

- 用户要求搜索、查找、列出或扫描招标、中标、采购意向、合同等公告。
- 用户基于上一批结果说“继续”“改成深圳”“只看在招”“排除维保”等。
- 用户要求“搜全一点”“不要漏项”“按相关性分组”。

以下场景不使用本技能：

- “哪些值得跟进”转入 `tender-opportunity-analysis` 的重点筛选。
- “分析第 N 个项目”转入单项目深度分析；需要补详情时继续使用 `tender-search`。

## 执行顺序

1. 普通新查询读取 `references/query-plan.md`，生成 `QueryPlanV1`。
2. “继续”或界面选择“继续查看下一批”直接读取并校验上一轮 `continuationState`，禁止重新解释检索条件。界面提交文字会由外层智能体标准化为“继续”后再进入本工作流。
3. 其他连续追问按字段覆盖规则合并旧计划，只修改用户明确改变的字段。
4. 读取 `references/retrieval-ranking.md`，构造原词、受控扩展、全文补漏以及按需纠偏请求。
5. 读取 `references/output-continuation.md`，只把当前最多 20 条投影结果交给回答阶段。

## 不可违反的规则

- 地区、绝对日期、金额、公告阶段、采购方、中标方和明确截止状态是硬条件；每轮完整继承。
- 第一轮优先完整业务短语；扩展词按独立概念组组织，必选组之间为 AND，组内为 OR。
- 不把“在招”解释成“未截止”。“在招”默认阶段为 `[4]`；“未截止”必须有截止日期证据。
- 每个搜索轮次只请求 `page_size=50` 的第一页，最多三轮基础查询和一次纠偏；返回结果全部在本地标准化、筛选、去重和分层，不对单条结果调用详情接口。`total` 大于已加载数量、任一轮失败或只拿到局部时设置 `is_complete=false`。
- 计费型搜索请求禁止自动重试；余额不足、认证失败或限流后立即停止后续轮次。
- 同一公告去重与同一项目生命周期归并是两件事；采购意向、招标、中标、合同等阶段都要保留。
- A 严格匹配、B 高相关、C 可能相关。A/B 进入主结果，C 只能进入独立折叠区。
- 每条结果必须有 `record_key` 和匹配证据。排序必须稳定，连续批次不得因重新搜索漂移。
- 当前批次必须整体进入 `resolve_tender_source_urls_v2`。只使用工具返回的 `display_url`，不得自行拼接链接；`SOURCE` 时项目名称必须直链 `display_url`，`NONE` 标为“原文暂未解析”，禁止把聚合页展示为用户可点击来源。
- 回答模型不得接收原始 API 响应、公告全文、网页 HTML、完整候选集合、认证信息或内部推理。
- 回答阶段在普通检索结果末尾生成一张 UIP 下一步选择卡片：有剩余结果时提供“继续查看下一批、只看仍可报名的项目、筛选最值得跟进的项目、调整地区、时间或阶段”；没有剩余结果时去掉“继续查看下一批”。卡片只承载用户可见的业务动作，不包含 `continuationState`、查询条件、链接解析细节或任何内部字段。

## 失败降级

- 计划校验失败时只重试一次；仍失败则保留硬条件，以用户完整原词执行单轮降级查询并明确“不完整”。
- 某轮或某页失败时保留已取结果，记录失败轮次和页码，不宣称全量。
- 上游没有传入合法 `continuationState` 时，“继续”必须说明上下文已缺失并重新搜索，不能伪装顺序连续。
- 链接键集合不一致或原文未解析时，保留 `record_key` 与失败原因，不按数组位置合并，也不以聚合页作为用户链接回退。
