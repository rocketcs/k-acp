# 智能问数助手：查询流程评估与「问题不明确时」处理方案

> 状态：**方案评审稿（挂起，未落地）**
> 适用范围：`default-graphify-data-query`（医保问数 / 医药问数助手）
> 相关代码：`skills/skills/medical-catalog-question-semantics/`、`ui/src/features/graphify-data-query/`、`ui/src/components/chat/MessageItem.vue`
> 目标：先对齐「当前查询流程是否合理」，再决定是否落地澄清方案。

---

## 1. 目标与背景

用户希望问数助手把**自然语言问题**正确解析并查询出**真实数据**，最终以**数据表格 / 数据详情**的形式呈现，而不是过度总结、丢失数据格式。

用户同时特别关心：**“用户问题总有不会那么明确的时候，怎么处理？”** —— 即当解析不确定、口径有歧义时，系统应该怎么做，而不是硬猜或直接失败。

本文档先把完整流程拆解清楚，再评估**当前实现是否合理**（结合 k-acp 项目实际），最后给出建议方案与提示词写法。

---

## 2. 智能问数完整流程拆解

一条「自然语言 → 语义解析 → 图谱/MDL → 查询 → 答案」的问数流水线，结合本项目实际能力，归并为 6 个阶段：

| # | 阶段 | 图中内容 | 本项目落地载体 |
|---|------|----------|----------------|
| 0 | **输入** | 自然语言问题、连续追问、文件上传 | 会话消息 + 上下文 |
| 1 | **实体识别** | 自然语言 → 业务词典 → 实体标注 → MDL 实体对齐（`销售额→sales_amount`） | `semantic_context(dataset_id, question)` 返回命中的模型 / 字段 / 口径 / `trace_id` |
| 2 | **意图识别** | 指标对比 / 趋势分析 / 明细下钻 / 枚举 / 详情 | skill「问题解析工作流」第 1 步 |
| 3 | **查询规划** | 实体+意图 → 图谱查询语句（`MATCH (m:指标{name:'销售额'})-[r]-(n)`）/ MDL SQL → 过滤/聚合/排序 | 构造 `medical_catalog` MDL SQL |
| 4 | **执行** | 结构化检索（口径/来源/词典）作为提示 → 查询执行 | `query_preflight` → `query`（带 `trace_id`） |
| 5 | **答案生成** | LLM 基于结果生成答案，支持下钻/口径/来源引用 | 结果以 Markdown 表格/详情完整呈现 |

流程图底部每个步骤的产出，对应一条清晰的审计链路：

```
1 原始问题        上半年华东区域销售额同比增长多少？
2 实体识别结果    销售额 • 华东区域 • 上半年
3 意图识别结果    指标对比 • 区域筛选 • 同比计算
4 查询语句        MDL • 关系路径 • 查询语句
5 最终答案        智能问数答案
```

## 3. 当前查询流程评估

### 3.1 当前实现的真实链路（已核实）

1. **Skill 驱动**：`medical-catalog-question-semantics` 规定了「问题解析工作流 + 工具协议」。
   - 意图识别 → 目录域判定 → 字段落点 → 直接构造 MDL SQL。
   - 工具协议：`semantic_context` → `query_preflight` → `query`（**已移除模板 SQL，改直接 query**）。
   - 已定义 `status: "resolved" | "needs_clarification"`，明确「无法落点 → 输出澄清、不执行」。
2. **前端渲染**：`GraphifyDataQueryChat.vue` 用 `messagePresentationAdapter` 返回 `kind:'markdown'`，助手正文经 `MessageItem.vue` 里的 **`MarkdownRenderer`** 渲染。
   - `MarkdownRenderer` 基于 `marked`，**支持 Markdown 表格**，且**支持 UIP 交互卡**（`choice` / `form` / `confirm`，通过 `@interaction-submit` 上报）。
3. **数据呈现**：助手正文里的 Markdown 表格 / 详情会直接渲染，数据不丢失。

### 3.2 评估结论：当前流程总体合理，但有 4 个短板

| 维度 | 结论 | 说明 |
|------|------|------|
| ✅ 流程骨架（识别→规划→执行→生成） | **合理** | 与业界 Text-to-Query 一致，链路清晰、可审计 |
| ✅ 直接 query 替代模板 SQL | **合理** | 减少模板维护，SQL 完全受预检保护 |
| ✅ 数据用 Markdown 表格/详情呈现 | **合理** | 不丢数据格式，已与需求对齐 |
| ⚠️ **问题不明确时的处理** | **短板** | 有 `needs_clarification` 状态，但**没有落到结构化的交互闭环**（见 3.3） |
| ⚠️ 澄清内容形式 | **短板** | 「输出一个简洁澄清问题」是**纯文本**，未使用项目的 UIP choice/form 追问卡 |
| ⚠️ 澄清触发标准 | **短板** | 仅「无法落点」触发；对「意图/粒度/口径歧义」没有明确、可复用的触发规则 |
| ⚠️ agent 执行的确定性 | **风险** | 历史上出现过「拿到语义上下文后不执行最终 query」的情况（已通过强制规则缓解，仍需观测） |

### 3.3 当前「问题不明确时」最关键的缺口

现网行为大致是：**让 LLM 输出一段文本性的澄清问题**（或不澄清、犯错地强行查询）。没有：
- 结构化的**追问交互卡**（choice 点选 / form 补填）；
- 对「何时澄清 vs 何时自行判定」的**明确决策规则**；
- 与前端 UIP 渲染 / `needs_clarification` 状态的**闭环对接**。

→ 这正是用户担心的“问题不明确时怎么办”的核心缺口，也是本方案要补的部分。

## 4. 建议方案

### 4.1 核心原则

> **“问题不明确 → 先结构化澄清，再查询” 应成为流程的正式节点，而不是失败分支。**

澄清（asking-back）不是「再问一句」，而是用项目已具备的 **UIP 交互卡**让用户**点选 / 补填**，从而明确实体落点、意图、口径、粒度。

### 4.2 澄清触发条件（何时澄清，而不是硬查）

1. **关键实体无法落点**：词映射不到白名单字段，或多词对应多列且影响口径。
2. **意图/粒度不明确**：要「列表」还是「详情」？要「总额」还是「同比」？时间口径是「上半年」还是「本年度」？
3. **维度/筛选缺失但有歧义**：区域、时间等没说，且默认值会显著影响结果。
4. **口径/来源有多个解释**：含税 vs 不含税、在册 vs 在用、某个分类归属有歧义。

### 4.3 澄清交互载体（UIP 追问卡）

- **能枚举的歧义**（区域、时间、支付类别、粒度）→ **`choice` 选择题**：给出候选 + `allowCustom` 允许自定义输入。
- **需补多个字段**（如“帮我看下这个药”→ 名称? 企业? 类别?）→ **`form` 表单**补填。
- **决策口径确认**（执行一个不可逆/影响大的口径）→ **`confirm` + HITL 确认**。

每次澄清**只聚焦 1~3 个最关键的不确定点**，不一次抛一堆；历史选择可复用，减少反复追问。

### 4.4 与现有状态机对接

- skill 已有 `status: "needs_clarification"` → 细化为其产生 **UIP 追问卡**（而非纯文本）。
- `status: "resolved"` → 正常走 规划→执行→生成。
- 用户若坚持让系统自行判定 → 以**最合理默认口径**执行，并在答案中**明确披露口径假设**。

### 4.5 落地范围（三个文件）

| 文件 | 改动 |
|------|------|
| `medical-catalog-question-semantics/SKILL.md` | 加「澄清规则」章节：触发条件、choice/form 用法、needs_clarification 对接 |
| 问数主提示词（`agent_definition.system_prompt`，DB 侧 / 或 skill 内） | 内嵌澄清决策规则 + 追问卡写法 |
| 前端（如需） | 确认 `MarkdownRenderer` 已能渲染 UIP 卡（已具备），必要时补 HITL/确认闭环 |

> 提示：前端 `MessageItem.vue` 已用 `MarkdownRenderer` 渲染助手正文，**UIP choice/form 卡已可渲染**，所以大部分澄清能力可以通过**给 agent 写追问卡（纯内容）** 即可启用，前端改动可能很少甚至为零。

## 5. 提示词写法（结合本项目实现）

### 5.1 主提示词（端到端）

```
你是一个企业智能问数助手。你的任务是把用户用自然语言提出的业务问题，
解析为对已发布语义模型（MDL）与知识图谱的查询，并给出带数据依据的回答。

【总流程】对每个问题按以下顺序推进：
 0) 输入：接收用户的自然语言问题（支持连续追问、文件/上下文）。
 1) 实体识别：把用户措辞映射到已发布字段/业务模型（如 销售额→sales_amount），
    绝不杜撰字段名；拿不准时返回候选并等待澄清。
 2) 意图识别：判定 枚举/列表、详情、指标对比、趋势分析、统计、是否存在 等意图。
 3) 查询规划：由“实体+意图”构造查询语句——图谱关系路径或 MDL SQL；
    同时检索口径/来源/业务词典作为检索依据（结构化知识作为提示）。
 4) 执行：先 query_preflight 校验，allowed/warning 才 query；保留 trace_id。
 5) 答案生成：基于真实结果回答，数据以 Markdown 表格/详情完整呈现；
    支持图表、明细下钻、口径查看、来源引用；不得过度总结丢失数据格式。
```

### 5.2 澄清规则（内嵌主提示词）

```
【澄清规则——优先于硬性查询】
- 当解析不确定度影响查询结果或口径时，不得臆造字段/参数强行查询。
- 输出 needs_clarification，并用 UIP choice/form 追问卡给出结构化选项：
    · 能枚举的歧义（区域、时间、支付类别、粒度）→ choice 选择题（候选 + 允许自定义）。
    · 需补多个字段的歧义 → form 表单补填。
- 每次追问只聚焦 1~3 个最关键的不确定点。
- 澄清后再进入查询流程；历史选择可复用。
- 若用户坚持让系统自行判断，才以最合理默认口径执行，并在答案中明确披露该口径假设。
```

### 5.3 各子步骤独立提示词

**（a）实体识别**
```
从问题中抽取业务实体，映射到已发布语义模型字段，输出 JSON：
{ "entities": [{ "mention":"用户原词", "canonical":"已发布字段",
                 "domain":"DRUG/CONSUMABLE/SERVICE/DIAGNOSIS", "confidence":0-1 }] }
规则：只能映射白名单字段，禁止臆造列名；一词多列影响口径时列出候选；关键实体无法确定时标记 need_clarification。
```

**（b）意图识别**
```
判定用户意图，输出 { "intent":"...", "needs":["区域筛选","同比计算","结果排序"] }。
意图仅限：枚举/列表、详情、指标对比、趋势分析、统计、是否存在/比较。
维度缺失又有歧义时，返回候选意图并请求澄清。
```

**（c）查询规划**
```
根据 实体+意图 构造查询：
- 关系/图谱类：关系路径，如 MATCH (m:指标{name:'销售额'})-[r]-(n) RETURN m,r,n。
- 明细/指标类：MDL SQL，FROM 只能写 medical_catalog；目录域用 WHERE catalog_domain=... 过滤。
- 输出 { "query":"...", "filters":[...], "aggregations":[...], "sort":[...], "trace_id":"..." }。
- 规划无法满足用户歧义的口径时，停下来澄清，不硬排。
```

**（d）答案生成**
```
基于执行结果回答：先一句话结论，再完整呈现数据——列表类用 Markdown 表格，详情类逐字段列出；
不压缩数据格式，不省略已返回行；引用 trace_id/来源；截断时如实说明“部分结果”；图表/下钻/口径/来源用 UIP 呈现。
```

### 5.4 UIP 追问卡示例

「时间口径」歧义 → `choice` 卡：

```
{"role":"assistant","content":"为了给出准确结果，我需要确认几个口径。","version":"2.0",
 "interaction":{"id":"ask-time-region","type":"choice",
   "question":"你想按哪个时间口径统计「销售额」？",
   "multiple":false,"allowCustom":true,"autoSubmit":true,
   "options":[
     {"value":"H1","label":"上半年（1-6月）"},
     {"value":"2026H1","label":"2026 上半年"},
     {"value":"Q2","label":"二季度"}]}}
```

需补多个字段 → `form` 卡：

```
{"role":"assistant","content":"请补充查询条件","version":"2.0",
 "interaction":{"id":"drug-detail","type":"form","schemaVersion":"1",
   "fields":[
     {"name":"catalog_name","label":"药品名称","type":"text","required":true},
     {"name":"enterprise","label":"生产企业(选填)","type":"text"},
     {"name":"domain","label":"目录领域","type":"choice","options":[...]}]}}
```

## 6. 评估：落地收益与成本

### 收益
- **问题不明确时不再硬猜/失败**，通过结构化卡片引导用户，提升命中率与体验。
- **澄清内容可复用**，减少反复追问；口径更准确。
- **复用现有能力**：`needs_clarification` 状态、UIP 交互卡、`MarkdownRenderer` 均已具备，落地多为「内容/规则」级改动。

### 成本 / 风险
- **skill + 提示词改动**（低风险，纯内容）。
- **前端改动可能很少**（UIP 已能渲染），但需验证 HITL/确认闭环在问数场景是否需要。
- **agent 执行确定性**仍需观测（历史出现过不执行最终 query），澄清规则应放在“执行”之前强制。
- 需要先确认：问数助手**是否真的把「澄清交互」通过会话下发并回填**（验证 `interactionSubmit` 链路），再做前端调整。
