# 商业标书智能体高召回检索工作流设计

## 背景

当前商业标书智能体已经具备 `tender-search`、当前日期查询、公共 HTTP 请求以及分阶段商机分析能力，但普通搜索仍主要依赖模型一次性解释问题并调用一次查询。对于“广东近一个月统一运维、全部阶段”这类条件较多、业务词边界模糊的问题，单次查询容易出现以下偏差：

- 用户硬条件在扩词时丢失，例如地区、时间或公告阶段被放宽。
- 关键词被扁平化为大量 OR 条件，召回增加但噪声显著上升。
- 只取接口第一页，却把局部结果表达成全部结果。
- 同一公告重复出现，或同一项目的不同采购阶段被错误删除。
- 查询结果与知了标讯 Agent 的头部结果差异较大，也缺少可量化的对齐标准。

本设计在 K-ACP 应用层新增一个确定性的高召回搜索工作流，使商业标书智能体的检索条件、头部结果和知了标讯 Agent 保持高度一致，同时保留经过验证的额外有效结果。

## 用户认可的设计决策

1. 检索准确度和覆盖度优先，允许一次搜索执行二至四轮查询策略。
2. 采用双目标：头部结果与知了标讯 Agent 高度一致，同时保留其未展示的有效公告。
3. 结果采用三级相关性：A 严格匹配、B 高相关扩展、C 可能相关。
4. A、B 进入主结果；C 进入折叠区，避免弱相关结果污染首屏。
5. 只增加应用层配置，不修改 Java 后端源码、数据库结构或现有标讯接口。
6. 采用“Skill 生成计划，K-ACP 工作流保证执行”的实现方式。

## 目标

- 忠实解析用户的地区、时间、阶段、金额、主体角色、排除词和截止状态。
- 通过原词、受控扩词、全文补漏和按需纠偏降低漏项率。
- 所有查询轮次严格继承同一组硬条件。
- 分页获取接口声明的完整结果，不将第一页冒充全量。
- 确定性完成公告去重、项目生命周期归并和 A/B/C 分层。
- 返回真实项目链接，并说明每条结果的匹配依据。
- 支持“改成深圳”“只看在招”“继续”等连续追问，保持条件和顺序稳定。
- 建立固定回归集，量化与知了标讯 Agent 的条件一致率和结果覆盖率。

## 非目标

- 不修改 `tender-search` 对应的外部 API。
- 不新增后端 Controller、Service、数据库表或内置 Java 工具。
- 不修改其他智能体的搜索行为。
- 不把知了标讯 Agent 的展示结果当作绝对真值。
- 不在本阶段实现投标文件编制、自动联系采购方或自动创建监控任务。
- 不在普通搜索中自动执行单项目资格、技术和竞争风险深度分析。

## 应用层职责划分

### 商业标书智能体系统提示词

系统提示词只负责意图路由和用户交互边界：

- 普通标讯检索或市场扫描调用高召回搜索工作流。
- “哪些值得跟进”继续调用现有商机筛选能力。
- “分析第 N 个项目”继续调用现有单项目分析能力。
- 连续追问沿用最近一次 `QueryPlan`、结果顺序和分页状态。
- 面向用户只展示业务结果和查询口径，不展示接口参数、认证信息或内部推理。

### `tender-search`

共享技能继续作为标讯 API 的参数和数据字段契约，保持内容与绑定不变。它负责说明：

- `query_bids_advanced` 的关键词组、排除词、地区、日期、金额和阶段参数。
- `match_modes` 与采购方、中标方、标题、标的物、全文等字段的映射。
- 项目详情、企业分析和市场分析接口的使用方式。
- 真实项目 URL 的输出边界。

### 新增 `tender-high-recall-search` Skill

该技能只绑定商业标书智能体，负责：

- 从自然语言生成结构化 `QueryPlan`。
- 维护硬条件、业务概念组、扩展词和排除词。
- 决定三轮基础查询以及第四轮纠偏的触发条件。
- 定义 A/B/C 分层、匹配证据和用户输出模板。
- 明确错误降级、连续追问和分页规则。

该技能不得复制 API 地址、认证头和完整参数文档；接口细节仍由 `tender-search` 负责。

### 新增 K-ACP 工作流“商业标书高召回检索”

工作流负责确定性执行查询计划、分页、聚合、去重、归并、分层和质量检查。工作流内允许使用 K-ACP 的代码执行节点保存少量整理逻辑；该代码属于工作流应用配置，不进入后端源码，也不新增服务接口。

## 查询计划数据契约

查询计划 Agent 节点必须启用结构化输出并使用低温度。输出至少包含：

```json
{
  "original_question": "请查询广东地区近一个月统一运维全部阶段的招标信息",
  "subject": "统一运维",
  "hard_filters": {
    "provinces": ["广东"],
    "cities": [],
    "counties": [],
    "begin_date": "2026-06-22",
    "end_date": "2026-07-22",
    "bid_process": [1, 2, 4, 7, 8],
    "min_money": null,
    "max_money": null,
    "caller_names": [],
    "winner_names": [],
    "deadline_status": "all"
  },
  "concept_groups": [
    {
      "name": "服务组织方式",
      "required": true,
      "original_terms": ["统一"],
      "expanded_terms": ["一体化", "综合"]
    },
    {
      "name": "服务动作",
      "required": true,
      "original_terms": ["运维"],
      "expanded_terms": ["运行维护", "运营维护"]
    }
  ],
  "exclude_keywords": [],
  "inherited_fields": [],
  "assumptions": [],
  "correction_allowed": true
}
```

### 硬条件规则

- 地区、明确日期、金额、采购阶段、指定采购方或中标方均为硬条件。
- 所有查询轮次必须完整继承硬条件，不允许扩词时隐式放宽。
- 相对日期先通过当前日期能力解析，并按北京时间生成绝对日期。
- 普通“全部阶段”按知了标讯主要决策阶段解释为 `[1,2,4,7,8]`。
- 用户明确提到变更、候选人、验收、废标或“包含异常阶段”时，才追加 `[5,6,9,10]` 中对应阶段。
- “在招/正在招标”默认解释为招标阶段 `[4]`；“未截止/还能报名”才解释为截止状态条件，两者不能混用。
- 截止状态只有在列表字段、详情字段或公告原文中存在明确日期证据时才能判定。用户要求“未截止”时，无法核实的记录进入待核实区，不得混入 A/B 主结果。
- 缺少可安全默认的非关键字段时直接使用默认值；只有一个缺失条件会实质改变搜索范围时，最多追问一个问题。

### 查询计划到接口参数的映射

- 第一组业务词映射到 `keywords`，其余必选概念组映射到 `keyword_groups`；主关键词与每个关键词组之间为 AND，组内为 OR。
- 产品或主题默认使用 `match_modes=["title","sm"]`；采购方、中标方分别使用 `caller`、`winner` 角色字段，不能把公司名称作为普通全文词处理。
- `min_money`、`max_money`、`provinces`、`cities`、`counties`、绝对日期和 `bid_process` 直接继承 `hard_filters`。
- 第三轮才将匹配字段切换为 `fulltext`。切换字段不允许改变关键词逻辑或其他硬条件。
- 每轮实际请求参数由确定性的请求构造步骤从 `QueryPlan` 生成，搜索 Agent 不得自行改写硬条件。

### 连续追问规则

- “改成深圳”只覆盖城市，其他字段继承上一轮。
- “只看在招”只覆盖阶段，其他字段继承上一轮。
- “排除维保”追加排除词，不清空已有主题词。
- “继续”不重新解释问题，直接沿用查询计划、排序和分页游标。
- 每次输出保存本轮最终 `QueryPlan`、结果顺序、总数、已返回数和各轮分页游标。

工作流本身不新增服务端会话表。它将上述信息压缩为 `continuationState` 随工具结果返回，由商业标书智能体在同一对话的下一次工作流调用中原样传入。状态至少包含计划版本、稳定唯一键顺序、已展示位置、各轮页码、查询时间边界和失败标记；不得包含 API Key、公告全文或模型内部推理。后续批次优先按稳定唯一键通过详情接口补取展示字段；若只能重新请求列表页，则必须沿用原查询时间边界，并用已展示唯一键消除插入或重复。若上游未传入状态，“继续”必须提示上下文已缺失并重新搜索，不能假装顺序仍然连续。

## 四轮查询策略

### 第一轮：用户原词精确检索

目标是对齐知了标讯 Agent 的头部结果。

- 用户输入中的完整业务短语优先匹配 `title` 和 `sm`；例如“统一运维”先作为完整短语检索，不先拆成“统一”与“运维”。
- 只有用户原问题本身明确包含多个独立必选概念时，第一轮才使用 `keyword_groups` 表达 AND，组内同义写法使用 OR。
- 不在本轮加入弱相关上下位词。
- 本轮强命中记录默认进入 A 层。

### 第二轮：受控业务扩展

目标是补足不同采购单位对同一业务的不同叫法。

- 扩展词按对象、动作、行业或产品概念分别维护，不能压平成一个 OR 列表。
- 必选概念组之间继续使用 AND。
- 扩展词只来自技能中的受控词典、当前企业画像或用户已确认的业务词。
- 不能根据单次结果临时编造宽泛词，例如单独使用“平台”“系统”“服务”。
- 满足全部必选概念组的结果进入 B 层。
- 查询计划器不得创建语义重复的必选组；例如一个组为“统一运维”、另一个组仅为“运维”会造成伪 AND，应改为“服务组织方式”与“服务动作”等彼此独立的概念。

### 第三轮：全文补漏

目标是发现标题和标的物未写明业务词，但公告正文实际包含相关需求的项目。

- 使用原词和高可信扩展词进行 `fulltext` 检索。
- 仍然继承地区、日期、阶段、金额等硬条件。
- 仅全文命中或概念不完整的记录默认进入 C 层。
- C 层不参与头部排序，必须附带命中原因并折叠展示。

### 第四轮：动态纠偏

第四轮不是固定执行，仅在质量检查触发时运行：

- 前三轮合并后为零结果。
- A、B 合计少于 3 条，且 C 层存在同时覆盖全部必选概念组的候选。
- 前 20 条候选（不足 20 条时检查全部）中，未覆盖任何完整必选概念组的比例超过 30%。
- 某一查询轮次或分页失败，导致用户要求的阶段可能未完整获取；此时第四轮只重试失败范围，不改写查询口径。

纠偏动作只能选择一种最小变化：

- 放宽一个过窄的扩展词。
- 加入一个明确的上位词或下位词。
- 加入一个高频噪声排除词。
- 调整一个错误的字段匹配模式。

工作流必须记录纠偏原因和变化字段；不得悄悄改变地区、日期、金额或用户明确指定的采购阶段。

“覆盖概念组”和“无关候选”均按受控词典与实际命中字段计算，不交给回答模型凭感觉判断。阈值作为 `query_plan_version` 对应的可调应用配置，首版固定使用以上数值，回归评测后才能变更。

## 分页规则

“二至四轮”描述查询策略数量，不代表每轮只调用一次接口。

- 每轮读取接口返回的 `total`、`page` 和 `page_size`。
- 使用 LOOP 节点继续请求，直到本轮已获取数量达到 `total`，或接口明确没有下一页。
- 每页最大条数遵守接口限制，不通过猜测扩大 `page_size`。
- `query_bids_advanced` 的页码上限为 100、每页上限为 50；LOOP 必须设置最大 100 次安全上限。若 `total` 超过接口可遍历上限，返回 `is_complete=false` 和“接口分页上限”，不得声称已获取全量。
- 单次对话容量不足时，工作流仍保留完整结构化结果；回答显示总数、已展示数和剩余数。
- “继续”从保存的输出游标继续展示，不重新搜索导致顺序变化。
- 任何分页失败都标记对应轮次和页码，不把已获取部分称为全量。

数量口径必须区分：`round_reported_total` 为各轮接口声明数，`unique_loaded_count` 为跨轮去重后的实际加载数，`displayed_count` 为当前展示数。只有 `is_complete=true` 时才能把 `unique_loaded_count` 表述为“找到总数”；否则只能表述为“已找到至少 N 条”。

## 工作流节点设计

### 主流程

1. `START`：接收 `question`、`priorState` 和 `companyProfile`。START 参数名不使用下划线，内部 JSON 字段仍可使用下划线。
2. `AGENT / 查询计划器`：输出符合 Schema 的 `QueryPlan`，不直接调用标讯接口。
3. `CODE / 计划校验`：用 Java 校验必填字段、日期范围、阶段和概念组，输出 `valid`、`errors` 和规范化计划。
4. `IF_ELSE / 校验路由`：有效计划进入请求构造；无效计划按“重试一次后原词降级”分支处理。
5. `CODE / 请求构造`：用 Java 代码从已校验计划确定性生成各轮请求，不访问网络。
6. `LOOP + TOOL_EXECUTE 或受限 AGENT / 第一轮搜索`：执行原词精确查询和分页。
7. `LOOP + TOOL_EXECUTE 或受限 AGENT / 第二轮搜索`：执行受控扩展查询和分页。
8. `LOOP + TOOL_EXECUTE 或受限 AGENT / 第三轮搜索`：执行全文补漏查询和分页。
9. `VARIABLE_AGG`：聚合三轮响应及每条记录的来源轮次。
10. `CODE / 标准化整理`：用 Java 完成字段标准化、公告去重、项目生命周期归并、匹配证据、初始分层、质量指标和复合排序键。
11. `IF_ELSE / 质量检查`：根据标准化节点输出的 `needsCorrection` 判断是否进入第四轮。
12. `LOOP + TOOL_EXECUTE 或受限 AGENT / 第四轮搜索`：仅在触发时执行，再进入聚合整理。
13. `LIST_SORT`：按标准化节点生成的复合 `sortKey` 升序排序，实现相关层级、截止紧迫度、发布时间和稳定键的多级顺序。
14. `CODE / 状态封装`：生成不含敏感信息的 `continuationState`。
15. `AGENT / 回答生成器`：只使用整理后的结构化数据生成业务结果。
16. `END`：返回用户回答、最终 `QueryPlan`、结果状态、`continuationState` 和内部验收指标。

### 工具调用方式

优先复用当前商业标书智能体已经可用的 `tender-search` 能力和公共 HTTP 工具。`tender-search` 是查询契约而不是可直接执行的工作流工具：真正的请求由已注册 HTTP 工具、HTTP 节点或绑定该技能与 HTTP 工具的受限 Agent 完成。认证信息通过现有凭据机制提供，不得写入系统提示词、Skill、工作流正文或日志。

若 K-ACP 当前工具执行节点无法直接动态调用 `query_bids_advanced`，使用具备 `tender-search` 和公共 HTTP 工具的受限 Agent 节点执行单轮查询。该节点必须启用结构化输出、使用低温度，只返回接口结构化数据，不生成面向用户的分析文本。LOOP 使用计数模式、最大 100 次，并用“已获取数达到 `total`、接口无下一页或发生不可重试错误”作为终止表达式。

## 标准化、去重与项目归并

### 公告去重

同一公告按以下优先级生成唯一键：

1. `bid_id`
2. `uniq_key`
3. 已验证原文 URL
4. 规范化标题、采购方、公告阶段和发布日期组成的复合指纹

同一公告被多轮命中时只保留一条记录，但合并：

- 命中的查询轮次。
- 命中的原词或扩展词。
- 命中的字段。
- 各轮返回的非空补充字段。

### 项目生命周期归并

公告去重和项目归并是两个不同步骤。同一项目的采购意向、预招标、招标、中标和合同公告不能互相删除。

项目关联优先使用项目编号或采购编号；没有编号时，使用规范化标题、采购方、核心标的物和时间邻近度形成候选项目组。无法可靠确认时保持独立，并标记“可能属于同一项目”，不得强行归并。

## A/B/C 相关性分层

### A：严格匹配

满足以下任一条件：

- 用户原始业务短语在标题或标的物中直接命中。
- 所有必选原始概念组在标题或标的物中完整命中。
- 指定采购方、中标方或品牌以正确角色字段精确命中，并满足其余硬条件。

### B：高相关扩展

- 受控扩展词在标题或标的物中命中。
- 所有必选概念组均满足。
- 没有命中排除词。
- 每个概念组都能追溯到具体的标题或标的物命中词，不依赖回答模型的主观语义判断。

### C：可能相关

包括：

- 仅在全文中命中。
- 只满足部分概念组。
- 标题过于宽泛，需要查看原文才能确认。
- 业务边界存在合理但未验证的关联。

C 层项目必须展示命中原因和待核实点，默认放入折叠区。

## 排序规则

排序必须稳定、可重复：

1. A 层优先于 B 层，B 层优先于 C 层。
2. 同层中，仅对有明确截止日期证据的招标公告按“尚未截止且截止时间更近”排序；未知截止状态不得推断。
3. 采购意向按预计采购时间排序；已中标和合同按发布时间倒序。
4. 时间相同时按规范化项目标题和唯一键排序，保证“继续”时顺序不漂移。

普通搜索不使用不透明的 100 分制。用户只看到 A/B/C 标签和简短匹配理由。

## 用户输出设计

### 查询口径

回答开头使用业务语言展示：

- 查询主题及已使用的高可信扩展方向。
- 地区、绝对日期区间、阶段和排除条件。
- 找到的公告总数、A/B/C 数量和当前展示数量。
- 若发生纠偏，说明“为避免漏项，补充检索了某类相关表述”，不展示内部参数。

### 主结果

- 主表展示 A、B 层。
- 字段包括项目名称链接、采购方、地区、阶段、预算、发布时间、截止时间和匹配标记。
- 截止时间未返回或无法从公告中可靠确认时显示“待核实”，不得根据发布时间推算。
- 项目名称只使用接口返回或已验证的真实 URL。
- 同一项目跨阶段出现时，在项目下显示简短生命周期提示。

### 补漏结果

- C 层使用 `<details><summary>` 折叠。
- 每条说明全文命中词和需核实原因。
- 不能为了缩短回答删除 C 层数据。

### 连续操作

回答结尾根据当前状态最多给出三项：

- 继续查看剩余结果。
- 只看某阶段或某地区。
- 对某个项目执行深入分析。

## 错误和降级

### 查询计划无效

- Schema 校验失败后重试一次。
- 第二次仍失败时，退化为用户原词精确搜索。
- 回答标记“扩展检索未完成”，不得伪造扩展结果。

### 部分查询失败

- 保留成功轮次和已成功分页的数据。
- 明确说明失败的是精确、扩展、全文补漏还是某个页码。
- `is_complete=false` 时禁止使用“全部找到”“全量结果”等表述。

### 零结果

- 展示实际采用的地区、日期、阶段、主题词和主要扩展方向。
- 只给一个最小放宽建议。
- 不自动更换地区、时间或主题返回替代项目。

### 超长结果

- 显示接口总数、已加载数、已展示数和剩余数。
- 优先展示 A、B，C 和后续批次折叠。
- 不静默截断，不声称固定只返回 10 或 20 条。

### 链接不可用

- 优先使用已验证原文链接。
- 原文不可访问时保留聚合页链接并标记状态。
- 没有 URL 时使用纯文本项目名，禁止猜测链接。

## 对齐与验收方案

### 固定回归集

第一阶段建立 30 条代表性问题，覆盖：

- 单关键词、短语、同义词、上下位词和业务黑话。
- 省、市、区县和无地区条件。
- 相对日期、绝对日期和无日期条件。
- 全部主要阶段、只看在招、只看中标和指定异常阶段。
- 金额区间、采购方、中标方、品牌和采购方式。
- 多概念 AND、排除词和全文补漏。
- 公司简称、错别字和模糊主题。
- “改成深圳”“只看在招”“继续”等连续追问。

每条问题在知了标讯 Agent 和商业标书智能体分别执行，保存：

- 双方解析的查询条件。
- 知了标讯展示的结果及顺序。
- 本工作流 A/B/C 结果及唯一键。
- 双方不一致项目的公告原文抽查结论。

### 发布门槛

| 指标 | 目标 |
|---|---:|
| 用户硬条件解析准确率 | 100% |
| 知了标讯头部结果覆盖率 | ≥ 95% |
| A/B 层人工准确率 | ≥ 90% |
| 公告重复率 | < 1% |
| 静默截断率 | 0 |
| 缺失字段编造率 | 0 |

“额外有效发现率”作为观察指标：统计商业标书智能体比知了标讯多找到、且经公告原文确认有效的项目。该指标不设硬性下限，但每个额外项目必须能够追溯到命中词、查询轮次和真实来源。

其中“知了标讯头部结果”固定指每条回归问题在同一时间窗口内首次展示的前 20 条去重公告；不足 20 条时取全部。双方使用 `bid_id → uniq_key → URL → 复合指纹` 对齐。头部覆盖率按 30 条问题合并后的交集数除以知了标讯有效参考公告数计算，同时记录每题覆盖率，避免总体数字掩盖单题失效。A/B 人工准确率以抽查公告原文后确认属于用户业务范围的数量除以抽查 A/B 数量计算。

### 差异判定原则

知了标讯 Agent 是头部结果参考，不是绝对真值。双方结果不一致时：

1. 先比较硬条件和匹配字段。
2. 再查看公告原文是否真正属于用户业务范围。
3. 属于有效补漏的项目保留，不为提高表面相似度而删除。
4. 属于噪声的项目用于更新受控词典、排除词或概念组规则。

## 可观测性

工作流应在内部结果中保留但不直接向业务用户展示：

- `query_plan_version`
- 每轮查询类型、耗时、总数和分页数
- 每条公告的来源轮次和匹配字段
- 公告唯一键和项目组键
- 是否执行纠偏及原因
- `is_complete`、失败轮次和失败页码
- A/B/C 分层结果

这些字段用于回归测试和问题诊断，不包含 API Key、认证头或模型内部推理。

## 安全与隔离

- API Key 只通过现有凭据或运行环境注入，不进入提示词、Skill、工作流正文和对话输出。
- 新 Skill 和工作流只绑定商业标书智能体。
- 共享 `tender-search` 保持不变，避免影响其他智能体。
- 工作流代码节点只处理已返回的结构化标讯数据，不执行网络访问、文件写入或外部副作用。
- 普通搜索只读，不自动收藏、监控、联系采购方或发送消息。

## 实施范围

后续实施计划仅包含以下应用层工作：

1. 创建并导入 `tender-high-recall-search` Skill。
2. 在 K-ACP 中创建“商业标书高召回检索”工作流。
3. 配置查询计划、三轮搜索、纠偏、分页、聚合、代码整理、排序和回答节点。
4. 更新商业标书智能体的短系统提示词和能力绑定。
5. 保留现有 `tender-search`、`tender-opportunity-analysis`、当前日期和 HTTP 能力。
6. 建立 30 条回归问题及双方结果对照表。
7. 调优受控词典、排除词和质量阈值，直到达到发布门槛。

不包含任何后端源码、数据库结构或外部标讯 API 修改。

## 验收示例

输入：

```text
请查询广东地区，有关统一运维的招标信息，时间范围为近一个月，全部阶段的招标信息
```

预期：

- 查询口径显示广东、北京时间近一个月、主要阶段 `[1,2,4,7,8]`。
- 执行原词、受控扩词和全文补漏，必要时才执行第四轮。
- 所有轮次保持相同地区、日期和阶段。
- 接口多页时继续分页，不只使用第一页。
- A/B 主表与知了标讯头部结果覆盖率达到目标。
- C 层折叠展示有效补漏，不污染主表。
- 同一公告不重复，同项目不同阶段保留并关联。
- 每个项目使用真实链接，缺失字段不编造。
- 回答显示总数、已展示数和剩余数，不静默截断。

连续追问：

```text
只看深圳正在招标的
```

预期：只覆盖城市和阶段，沿用主题、日期、扩词和排除条件，重新执行工作流并返回稳定排序结果。
