# 问标助手 UIP 卡片前端稳定性设计与实施说明

## 状态

提案，待评审。本文只描述前端改动；不修改 Java 服务端、工作流、模型配置、数据库或智能体提示词。

## 背景

问标助手在需要用户选择下一步操作时，会在模型文本中输出 ` ```uip ` 代码块。当前前端会把代码块提取为 UIP 卡片，但对失败的处理是展示“[UIP 解析失败]”和部分原始 JSON。模型偶发输出半截 JSON、重复 UIP 块或不完整字段时，用户因此会看到协议内容，而不是可操作卡片。

现有链路中还有一个关键问题：`useChatStream.ts` 仅通过文本是否包含 ` ```uip ` 判断问标回复是否已经包含后续卡片。一个无效 UIP 块同样会满足该判断，导致现有的 `TENDER_FOLLOW_UP_CARD` 兜底卡不被追加。

## 目标

- 问标助手需要卡片时，用户最终只能看到已验证的可交互卡片或问标默认卡片。
- 不展示原始 JSON、协议错误信息或“解析失败”界面。
- 流式结束、异常结束或断连收口后，不遗留永久骨架屏。
- 不改动后端，保持服务端与上游开源项目零差异。
- 不将问标助手的业务兜底卡注入其他智能体。

## 非目标

- 不保证模型永远不会生成坏 JSON；前端负责隔离和恢复。
- 不在浏览器中猜测、补全或修复截断 JSON。
- 不改变非问标助手现有的交互协议、提示词或业务流程。
- 不实现服务端 JSON Schema 校验、模型重试或 AG-UI 自定义卡片事件。
- 不修改历史库中已经保存的原始消息；历史消息在读取时按同一前端规则安全展示。

## 现状与根因

| 环节 | 当前职责 | 风险 |
|---|---|---|
| `ui/src/utils/chat/uip.ts` | 提取 `uip` 代码块，并以 `JSON.parse` 和 `interaction` 是否存在做基础判断 | 不能区分完整合法卡片与字段不全、类型未知或空选项的卡片 |
| `ui/src/components/markdown/uip/UIPRenderer.vue` | 失败时展示原始代码和“重新生成”按钮 | 把内部协议错误暴露给最终用户 |
| `ui/src/components/markdown/MarkdownRenderer.vue` | 将文本分为 HTML、Mermaid、UIP、VEP 片段 | 需要接收策略，才能对不同智能体采取不同处理 |
| `ui/src/composables/chat/useChatStream.ts` | 保存完成消息并为 `default-tender` 追加 `TENDER_FOLLOW_UP_CARD` | 仅根据代码围栏字符串判断卡片存在，坏块会错误抑制兜底 |

## 方案概览

采用“共享安全渲染 + 问标严格收口”两层前端策略。

```text
模型流式文本
  │
  ├─ 流式期间：仅显示正常文本；未完成 UIP 使用短暂骨架屏
  │
  └─ 消息完成/异常收口
       │
       ├─ 提取所有 UIP 块并执行协议校验
       │    ├─ 合法：保留
       │    └─ 无效：从展示和保存内容中移除
       │
       ├─ 非问标助手：保留兼容模式，不插入业务卡片
       │
       └─ 问标助手（agentCode = default-tender）
            ├─ 恰有一张合法卡片：保存并渲染该卡片
            ├─ 多张合法卡片：按确定规则仅保留第一张
            └─ 没有合法卡片：追加 TENDER_FOLLOW_UP_CARD
```

## 策略定义与隔离

新增纯前端策略概念 `uipPolicy`，由聊天页或流式消息处理层基于 `agentCode` 选择，而不是由公共组件自行判断业务身份。

| 行为 | 默认策略（其他智能体） | `tenderStrict`（`default-tender`） |
|---|---|---|
| 隐藏无效 UIP 的原始代码 | 是 | 是 |
| 已知基础类型校验 | 是 | 是 |
| 严格校验 choice/form/confirm 的必填字段 | 否，保持协议兼容 | 是 |
| 只保留一张有效 UIP 卡片 | 否 | 是 |
| 无有效卡片时追加默认业务卡 | 否 | 是，追加 `TENDER_FOLLOW_UP_CARD` |
| 流式结束后收口骨架屏 | 是 | 是 |

这保证共享组件不会将“问标下一步操作”泄漏给其他智能体。默认策略仅移除无法解析的协议块，避免用户看到原始 JSON；对于合法但使用未来扩展字段的卡片，仍交由现有渲染器兼容处理。

## UIP 严格校验规则

严格模式只接受一个顶层 JSON 对象，且必须包含非空 `content` 与 `interaction`。

通用规则：

- `interaction.id` 为非空字符串；
- `interaction.type` 只能是 `choice`、`form` 或 `confirm`；
- 禁止空对象、数组型 `interaction`、未知交互类型和空白 JSON；
- 解析失败直接判为无效，不进行 JSON 自动修复。

类型规则：

- `choice`：`question` 为非空字符串，`options` 为非空数组；每个选项有唯一非空 `value` 与非空 `label`。
- `form`：`fields` 为非空数组；每个字段有唯一非空 `name`、`label` 和受支持的字段类型；存在选项的字段不得有空选项。
- `confirm`：`message` 为非空字符串。

这些规则应封装为纯函数，返回“合法块、无效块、去除 UIP 后的文本”及原因码，不在 UI 组件中散落字符串判断。

## 消息完成与保存规则

问标助手的核心规则是：是否已经包含后续卡片，必须由“是否存在通过严格校验的 UIP 卡片”决定，而不能由 `displayText.includes('```uip')` 决定。

`TEXT_MESSAGE_END` 的处理顺序为：

1. 选择最终展示文本（高召回工作流答案优先，否则模型最终文本）。
2. 根据当前 `agentCode` 选择策略并规范化消息。
3. 移除无效 UIP 代码块；保留普通文本与合法 UIP 块。
4. 在 `tenderStrict` 下，若有多张合法卡片，只保留第一张；若没有合法卡片，则追加 `TENDER_FOLLOW_UP_CARD`。
5. 用规范化后的内容更新“本轮是否已有问标后续卡片”的状态。
6. 保存规范化后的内容，并清理流式状态。

历史消息走同一提取与安全渲染逻辑。即使数据库中保留了旧版本的坏 UIP，也不能再把其原始 JSON 展示给用户。

## 流式与异常收口

在 `uip` 代码块尚未闭合时，允许显示 UIP 骨架屏，避免逐字符展示 JSON。以下任一事件发生时，必须结束骨架屏并按最终策略重新计算：

- `TEXT_MESSAGE_END`；
- `RUN_FINISHED`；
- 请求异常、断连或用户停止；
- 有消息开始但未获得完整 UIP 块的超时场景。

问标助手在这些收口路径中，如果本轮已有业务答案但没有严格合法卡片，必须落到默认问标卡片。只有完全没有业务答复时，才不制造一张脱离上下文的卡片。

## 用户体验规则

- 不再显示“[UIP 解析失败]”、原始 JSON、协议字段或“重新生成”按钮。
- 已通过校验的卡片照常显示。
- 坏卡片与好卡片混在同一回复中时，只展示好卡片。
- 对问标助手，只有坏卡片或没有卡片时，展示现有的稳定下一步操作卡。
- 其他智能体发生坏 UIP 时，保留其普通文本，不追加问标业务操作。

## 实施范围

实施仅涉及 `ui/`：

1. 在 `ui/src/utils/chat/uip.ts` 增加纯函数校验、提取结果和按策略规范化函数。
2. 为这些函数增加 Node 单元测试，覆盖完整、截断、未知类型、空选项、重复卡片及历史内容。
3. 调整 `ui/src/composables/chat/useChatStream.ts`，使问标卡片存在性与保存内容均基于规范化结果。
4. 调整 `ui/src/components/markdown/MarkdownRenderer.vue` 与 `ui/src/components/markdown/uip/UIPRenderer.vue`，传递策略并使无效块静默跳过，不再展示原始协议。
5. 仅在 `agentCode === 'default-tender'` 时启用 `tenderStrict`。
6. 完成测试、类型检查与前端构建后，仅重建测试环境的 `k-acp-local-apboa-frontend` 容器。

不修改 `engine/`、`workflow/`、数据库结构、接口合同或部署编排。

## 测试与验收

### 单元测试

- 合法 choice、form、confirm 卡片通过严格校验。
- 截断 JSON、无 `interaction`、未知类型、空 options、重复 option value、空字段数组均被拒绝。
- “坏 UIP + 好 UIP”仅保留好 UIP。
- “仅坏 UIP”在问标严格模式下得到默认卡片。
- “仅坏 UIP”在默认模式下不会得到问标卡片。
- 多个合法 UIP 在问标严格模式下只保留第一张。
- 普通 Markdown 文本不被修改。

### 集成验证

1. 未登录以外的正常问标检索：正常文本和一张可操作卡片同时显示。
2. 人工构造截断 `uip` 代码块：不出现 JSON、错误提示或永久骨架屏；问标助手显示默认卡片。
3. 人工构造“坏块 + 合法块”：只显示合法块，不追加重复默认卡。
4. 切换到非问标智能体并发送同样内容：不出现问标默认卡。
5. 重开一条包含旧坏 UIP 的历史会话：不显示原始 JSON。

### 发布验收

- `ui` 单元测试通过；
- `npm run type-check` 通过；
- 前端生产构建通过；
- 测试环境仅更新 `k-acp-local-apboa-frontend`；
- `http://192.168.8.81:23080/web/` 健康检查返回 200；
- 手工验证问标助手的坏卡片、正常卡片和历史消息三种路径。

## 风险与回滚

| 风险 | 控制措施 |
|---|---|
| 严格规则误拒绝问标助手未来新增卡片 | 严格模式仅限 `default-tender`；新增类型时同步扩展校验器和测试 |
| 默认卡片与模型卡片重复 | 只依据严格校验后的有效卡片决定是否追加 |
| 流式状态未结束 | 在消息结束、运行结束、异常和停止路径统一收口 |
| 前端升级出现行为问题 | 仅替换前端镜像；使用已保留的前端回滚镜像恢复 |

回滚只需将测试环境的 `k-acp-frontend` 容器恢复到本次发布前的前端镜像；后端、数据和工作流均未改变。

## 决策记录

选择纯前端方案的原因是避免对开源后端产生本地补丁差异。该方案保证“稳定展示与恢复”，不宣称能够约束模型永不产生坏 JSON。若未来需要为移动端、开放 API 或多个前端提供同一保证，再将协议校验演进到服务端输出层。
